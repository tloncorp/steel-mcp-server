# Steel MCP Server v2 — Research Synthesis

**Prepared:** 2026-07-27
**Inputs:** seven parallel research tracks (mcp-protocol, browser-mcp-local, browser-mcp-cloud, hosted-mcp-ops, distribution, agentic-browsing, steel-surface); four adversarially fact-checked. Refuted claims have been replaced with the fact-checker's correction throughout; where a correction and an original conflict, the correction wins and is marked.
**Audience:** whoever is about to write P0.
**Companion doc:** `PLAN.md` (draft, branch `niko/steel-mcp-server-v2`). This document contradicts PLAN.md in several load-bearing places. Read §2 before writing code.

## 1. Bottom line up front

1. **MCP 2026-07-28 ships tomorrow and deletes the mechanism PLAN.md is built on.** Protocol-level sessions and `Mcp-Session-Id` are gone (SEP-2567). The `initialize` handshake is gone (SEP-2575). `DELETE /mcp`, the standalone `GET /mcp` SSE stream, and `Last-Event-ID` resumability are gone. The spec's prescribed replacement — "explicit, server-minted handles passed as ordinary tool arguments" — uses *"an open browser context"* / *"a Playwright browser instance"* as its worked example. The spec authors wrote the design guide for Steel's exact problem. Adopt it verbatim.

2. **Rewrite the session model around an explicit `session_id` handle before writing any transport code.** `browser_session_create` mints and returns it; every stateful tool takes it as an argument; `(handle, org)` is re-authorized on every single call. This deletes the Redis session binder, deletes sticky-routing concerns, unblocks multi-browser concurrency, and — critically — is the only design that works on ChatGPT and claude.ai, which already close the MCP session between consecutive tool calls today (playwright-mcp#1045).

3. **The billed-session-leak problem is already solved, server-side, by Steel.** `inactivityTimeout` shipped in changelog #028 (2026-06-06) as a session-creation parameter. Set `timeout` + `inactivityTimeout` at create and the browser releases itself even if our process dies, our replica is rescheduled, and the client vanishes. Our reaper becomes an optimization, not the safety net. PLAN.md §5 spends its most careful section rebuilding, more weakly, a thing that already exists.

4. **Several PLAN.md facts about Steel's own API are wrong** and will fail on first contact: the scrape param is `format` (singular) not `formats[]`; `links` is not a format value (always returned); `/v1/screenshot` and `/v1/pdf` return hosted `{url}` not bytes; the CDP URL needs `apiKey` as well as `sessionId`; there is no `metadata` field to tag sessions with; and the 30-minute hard TTL is illegal on the Launch plan (15-minute cap). Also: `@steel-dev/mcp-server` was never published to npm, so §11's migration plan describes a migration that does not exist.

5. **Ship a `browser_find` (cheap grep over the a11y snapshot) and default post-action snapshots to OFF.** These are the two highest-leverage token decisions available and PLAN.md gets both wrong. Full-snapshot-to-locate-one-button is the single dominant token waste in this category — it is the subject of ~10 sustained user complaints against Playwright MCP over eight months.

6. **Tool *count* is a vanity metric; schema *bytes* are the cost, and response bytes dwarf both.** Measured 2026-07-27: Playwright MCP default = 24 tools / 18,467 B; Chrome DevTools MCP = 29 / 23,245 B; Chrome `--slim` = 3 / 1,028 B. Meanwhile `playwriter` exposes 2 tools and costs **49,472 B** — larger than Playwright's entire 69-tool surface. Measure and publish Steel's number; nobody in the category does.

7. **Primitives + batching beats natural-language actions.** The only measured evidence for a "one big tool" architecture (Browserless Agent's six-benchmark sweep) attributes the win to round-trip elimination, not to an internal agent loop. Steel gets that win from a `browser_batch(steps[])` tool and `include_snapshot` on action tools, without ever putting an LLM in the product. Browserbase's `act`/`observe`/`extract` costs an inference per call, is nondeterministic, and adds latency — and they shipped no migration guide and no release in the four months since.

8. **Ship a coordinate/vision surface, but as an opt-in second profile, never as the default.** Computer use became a *native interleavable tool* inside frontier models in 2026 (Gemini 3.5 Flash, GPT-5.4+), so a host can hold both Steel's structured tools and its own pixel loop in one conversation. Steel does not have to choose. Back it with Steel's own `POST /v1/sessions/{id}/computer` endpoint (which PLAN.md does not mention), do the downscaling server-side at 1280x720, and include a `zoom(region)` action.

9. **Prompt injection is the largest unmitigated risk in the design, has no protocol-level answer, and is therefore the clearest differentiator available.** The spec's Security Best Practices page says nothing about it. Playwright MCP's README says "not a security boundary." Browserbase's injection advisory (#159) was never actioned and then the repo was archived. Meanwhile Google measured a 32% relative increase in malicious injected content Nov-2025→Feb-2026 and Unit 42 catalogued 22 delivery techniques in the wild. Steel returning provenance-tagged, delimiter-fenced, invisible-content-stripped page text would be visibly more responsible than every competitor.

10. **OAuth deferral is a distribution decision, not a technical one, and it should be stated as such.** Bearer auth reaches Claude Code, Cursor, VS Code, Zed, Goose, the MCP Registry, VS Code's gallery, and Cursor's marketplace. It does *not* reach the Anthropic Connectors Directory or the OpenAI Plugins Directory — the two largest consumer surfaces. When Steel does build OAuth, build **Client ID Metadata Documents**, not Dynamic Client Registration: RFC 7591 DCR is now deprecated.

### 2.2 Steel's own API — PLAN.md has factual errors

| PLAN.md says | Correction |
|---|---|

Valid values: `html` \| `readability` \| `cleaned_html` \| `markdown`. Default `html`. **`links` is not a format** — every response always returns `content`, `metadata` (statusCode, title, OG tags, jsonLd) and `links: [{url,text}]`. `readability` yields an object, not a string. You must fetch-and-encode, or return a resource link. This is an unmade design decision, not a detail. |

Other Steel facts worth having: session release is `POST /v1/sessions/{id}/release` (PLAN.md is right); an undocumented `DELETE /v1/sessions/{id}` also works but returns a different body shape — don't use it. Headful is now the default for all sessions; managed browsers run Chromium 150. Projects with project-scoped API keys shipped in #029, so §4's "key → org" is now "key → project within org".

**Pricing (verified against steel.dev/pricing; one dossier track had fabricated numbers here — do not use them):** Launch = $0/mo + usage, $30 one-time credits, 10 concurrent sessions, 15-minute max session, 60 RPM, 7-day retention. Scale = $250/mo + usage, $100/mo credits, 100 concurrent, 1-hour max session, 600 RPM. Enterprise = custom, 1,000+ concurrent, up to 24h. Browser hours $0.10/hr billed per minute rounded up; Browser Tools $5/1k calls; proxy $10/GB; CAPTCHA $3/1k. Browser Tools are separately capped at 20 req/min per org. Hobby/Starter/Developer/Startup are retired legacy names (Steel's own proxies doc and installed skills still use them — file a docs fix).

**This reframes the leak argument.** A fully leaked 15-minute Launch session costs **$0.025**. One Browser Tools call ($0.005) costs roughly *three minutes* of browser time. So: scrape-first is right on latency, context size, concurrency-slot pressure and leak risk — and backwards on dollars. The scarce resource is the 10-concurrent-session cap and the 20 RPM Browser Tools limit, not money. Frame the reaper as **slot reclamation** and the design pressure lands correctly.

### 2.3 Distribution — facts that change sequencing

- **The Anthropic Connectors Directory requires OAuth 2.0** for authenticated services (`oauth_dcr` or `oauth_cimd` out of the box). `static_headers` (a fixed API key entered by an org admin) exists but is **beta and org-admin-scoped**, so individual Pro users cannot use it. Pure `client_credentials` M2M is explicitly unsupported. Anthropic recommends CIMD over DCR for high-traffic directory servers.
- **The submission portal requires a Team or Enterprise claude.ai org** just to open. "Admin settings aren't available on individual plans." This is a procurement dependency with real lead time. The Console path (`platform.claude.com/plugins/submit`) works for *plugins* without a claude.ai Team org, but not for remote connectors.
- One Anthropic connector submission reaches **five surfaces**: claude.ai, Claude Desktop, Claude Mobile, Claude Code, and **Cowork** (a research-preview product bringing Claude Code to non-engineers, launched 2026-01-12). Listing copy must read to a non-engineer. "Cloud browser infrastructure for AI agents" will not land in Cowork; "let Claude read and act on any website, including ones that block bots" will.
- **Anthropic review criteria constrain tool design:** every tool needs a `title` plus `readOnlyHint: true` or `destructiveHint: true`; names ≤64 chars; **a catch-all tool accepting both safe and unsafe methods is rejected** ("Do not ship a catch-all `api_request` tool with a method parameter"); generic errors like "Internal Server Error" fail review; reviewers run every tool with your test credentials; missing privacy policy = immediate rejection. Notably, the directory does **not** require domain-ownership proof — that applies only to the open Registry.
- **Claude Code enables MCP tool search by default**, deferring tool definitions until searched. The server **`instructions`** field is therefore now the primary discovery surface, and PLAN.md does not have one. Both tool descriptions and server instructions are **truncated at 2KB each**. Tool search is *disabled* on Bedrock, Google Cloud Agent Platform, Microsoft Foundry, and behind any custom `ANTHROPIC_BASE_URL` — so the full surface must also be tolerable loaded eagerly. That is a hard cap on tool count.
- **The Official MCP Registry** is live at `registry.modelcontextprotocol.io`, API frozen at v0.1, still formally **preview** (breaking changes / data resets possible; no GA date). It fully supports hosted servers via `remotes[]` with declared `headers[]` (`isRequired`/`isSecret`) — **no OAuth needed to list**. Apify's record (`com.apify/apify-mcp-server`, DNS-verified, updated the day it was checked) is the exact template. Steel has **zero presence**; `dev.steel/*` is unclaimed. Registry names are **immutable with no unpublish**.
  - Supported `packages[]` types are exactly five: **npm, pypi, nuget, oci, mcpb** (a dossier claim listing `cargo` was refuted).
  - npm ownership verification requires an **`mcpName` field in package.json** matching the server name. Easy to forget, blocks release day.
  - Namespace squatting is live: `com.mcparmory/browserbase` and `com.mcparmory/firecrawl` already exist as third-party records for competitors' names.
- **Publishing to the Official Registry is the VS Code + GitHub Copilot distribution path, transitively** — the GitHub MCP Registry ingests it, and VS Code's `@mcp` gallery is populated from GitHub's. There is no separate VS Code submission. This upgrades registry publishing from nice-to-have to load-bearing.
- **MCP Server Cards have NOT shipped** (a dossier claim said they had; refuted). SEP-2127 is an **open PR in Draft status**; the reference repo's README says in bold "not an accepted or official MCP extension." The design also moved: domain discovery is now an AI Catalog at `/.well-known/ai-catalog.json` (media type `application/ai-catalog+json`) referencing cards, with `GET <streamable-http-url>/server-card` as the reserved card location. `/.well-known/mcp/server-card.json` is the older SEP-1649 shape — **but Smithery reads exactly that path in production** as a scan-bypass. Serve it for Smithery; do not call it standards compliance.
- **OpenAI Plugins Directory** (serves ChatGPT **and Codex**) accepts MCP-only servers with no UI. Requires: Apps Management write access on an OpenAI Platform org; **verified individual or business identity** (unverified = rejection); production `/mcp` URL that the portal connects to and scans; domain verification via `/.well-known/openai-apps-challenge`; demo credentials working "without MFA, SMS, email confirmation, or private-network access"; accurate `readOnlyHint`/`openWorldHint`/`destructiveHint`; **five positive plus three negative test cases**; and you cannot submit a plugin referencing an already-published integration. *A "1–2 week review" figure circulating in the dossier is fabricated — the docs explicitly decline to give a timeline.*
- ChatGPT **Developer Mode** manual connectors: Plus/Pro individual users are limited to **read/fetch-only** custom connectors; write-capable ones require Business/Enterprise/Edu. Steel's read-only surface (scrape/screenshot/pdf) works for individuals; interactive browsing does not.
- **Cursor Marketplace** launched 2026-02-17 (Cursor 2.5). Every plugin is **manually reviewed** and **all plugins must be open source** (Steel is MIT — fine). Manifest needs only a `name` at `.cursor-plugin/plugin.json`. Team Marketplaces shipped in **2.6** (not 3.10, as one track claimed); 3.10 (2026-06-30) added Team *MCP servers* and Organizations within them. Deeplink format: `cursor://anysphere.cursor-deeplink/mcp/install?name=$NAME&config=$BASE64`. Note publicized deeplink RCE vulns around 3.9.8 (Proofpoint "CursorJack", Adversa "DeepJack") — users are warier of the button now.
- **`mcp-remote` is unmaintained** (0.1.38, 2026-02-05) and will not speak 2026-07-28. PLAN.md §11 points header-less hosts at it. Point them at Steel's own stdio entrypoint instead.
- **PulseMCP already lists "Steel Puppeteer" flagged Official**, pointing at a v1 that was never published to npm. That is a live, Anthropic-partnered directory advertising a broken install path today. Same-week fix, independent of everything else here.
- **`mcp.steel.dev` does not resolve** (NXDOMAIN as of 2026-07-27). All three review portals connect to the live URL during submission.

### 2.4 Things PLAN.md is right about, confirmed

Worth stating so nobody re-litigates them:

- **A11y snapshots over screenshots.** Unanimous across every vendor. Playwright's docs: 200–400 tokens vs 3,000–5,000. Browserbase *deleted* its screenshot tool. Playwright gates all six coordinate tools behind `--caps vision`; Chrome gates `click_at` behind `--experimentalVision`. Anthropic measured **no consistent uplift** from coordinate grids or tiled images — direct evidence against reviving v1's set-of-marks numbering.
- **Rejecting the v1 Web-Voyager loop.** More correct than the plan claims.
- **Scrape-first, stateless-first.** Independently converged on by Browserless (9 tools: 1 stateful + 8 stateless REST wrappers) and Cloudflare.
- **Hosted-first.** Browserbase archived its OSS MCP repo on 2026-07-20 and went hosted-only. Which also means…
- **Keeping a real OSS self-hostable server is now a genuine, uncontested differentiator**, not table stakes. Browserbase archived theirs; Hyperbrowser's has not been touched since 2025-11-20; the reference `@modelcontextprotocol/server-puppeteer` is deprecated and archived. The "actively maintained open-source browser MCP" slot is open.
- **Excluding `steel_execute_js` from the hosted default.** Playwright's equivalent is now literally named `browser_run_code_unsafe` and self-described as RCE-equivalent. (But see §4 — a blanket exclusion is wrong.)
- **Structured JSON to stderr** is now the officially recommended logging path.
- **~13 tools** sits in the winning band and below Claude Code's auto-tool-search threshold.

### 3.2 Where Steel differentiates, and the white space

**Four things nobody else has all of:**

1. **Credible open-source + self-hostable + hosted, all from one core.** Browserbase just vacated this position. Hyperbrowser abandoned it. The local-only servers (Playwright, Chrome, Firefox DevTools) can't offer hosted. Cloudflare and Kernel are hosted-only or hosted-first.
2. **Deterministic tools, no LLM in the product.** Browserbase pays an inference per `act`. That is nondeterminism, latency, and cost the user eats. Steel's tools are free to run and reproducible — *conditional on the a11y snapshot being good enough that the host's own model can drive it*. That makes `browser_snapshot` the single highest-risk component in the design.
3. **Server-side teardown as a marketed guarantee.** Playwright monorepo #41918 (82 orphan Chromium processes reparented to launchd after a normal day, ~4GB) was closed with "the problem seems to be on the client end." A local MCP server *structurally cannot* fix this. Steel owns both ends. And with `inactivityTimeout` Steel can offer it unconditionally. Publish it as an SLO, not an internal alert.
4. **Agent traces.** `GET /v1/sessions/{id}/agent-traces` returns a semantic timeline (click/input/navigate/scroll/error with `target.role`, `target.accessibleName`, `target.selector.css`, timestamps). No competitor has this. It turns "the click didn't work" into "the click landed at 12:04:18, then the URL became /challenge."

**The white space, ranked:**

- **A documented prompt-injection posture.** Nobody has one. The spec has no guidance. The two leaders disclaim it. Competitors are being publicly AIVSS-scored by MCPSafe (chrome-devtools-mcp 70/C, firecrawl 62/D, Browserbase 81/B down from 88 between February and May, with an open unresolved injection advisory). *Caveat: the chrome-devtools issues were closed by that team, so "publicly graded" is softer than it sounds.* Steel will get scanned the week it ships.
- **Keyless top-of-funnel.** Firecrawl proved the model. Steel's stateless scrape tools consume no session-minutes by construction — that is exactly the surface you can give away at a per-IP rate limit. No browser-infra competitor does this.
- **Published, measured token economics.** The incumbents' #1 complaint for eight months, unanswered. It's an afternoon of work to produce the table and it's a number, not a claim.
- **MCP Apps live session viewer.** Eleven hosts render `ui://` resources today, including Claude, ChatGPT, Cursor, VS Code and Goose. Steel's product *is* watching a browser work. Nobody in this category has shipped it.
- **MRTR human-in-the-loop.** Cloudflare and Human Browser market takeover; the new spec hands you the mechanism (`inputRequired.elicitUrl` → Steel session viewer); Steel already ships an embed-ready WebRTC player at `debugUrl` (`/v1/sessions/{id}/player`) with a parent-window postMessage API. *Correction (live probe, 2026-07-30): the `?interactive=true&showControls=true` params an earlier draft cited do not exist — the player reads only `hideOverlay` and `hideInteractionDialog`; interactivity comes from the session's server-side `debugConfig.interactive`, which is **on by default**. The player URL is an unauthenticated bearer capability: anyone holding it can watch and, with the default config, drive the browser.* This is arguably the highest-value thing a *browser* MCP server can do that a scraper API cannot.

**Two strategic reads worth internalizing:**

- **Both first-party vendors hedged MCP with a CLI within four months of each other.** Microsoft's README explicitly recommends `playwright-cli` + SKILLS over MCP for coding agents on token grounds; Google shipped a daemon-backed CLI plus six skills in the same npm package. Steel already ships a Rust CLI and five skills. PLAN.md's "one core, two entrypoints" should be **three**: hosted MCP, stdio MCP, and CLI+skills over the same core. Not wiring the existing skills to the v2 core leaves an asset stranded and ships two divergent implementations of the same semantics.
- **Two competitors decided the winning power-user move is to not build a tool surface at all** — Cloudflare and Oxylabs both document pointing Playwright MCP / chrome-devtools-mcp at their remote CDP WebSocket. Steel already has `wss://connect.steel.dev`. Documenting "Playwright MCP + Steel" costs a README section, covers the ~30-tool power-user surface Steel is deliberately not building, and hedges the largest technical risk in the plan.

## 4. Recommended tool surface for v2

### 4.1 Position on the framing questions

**Low-level primitives vs. high-level natural-language actions: primitives, plus batching.** Not a close call.

The only measured evidence for the high-level architecture is Browserless Agent's six-benchmark sweep (form fill 2m03s vs 3m42s–8m44s), and their own stated mechanism is *"a form with 8 fields doesn't need 10+ round trips"* — that is **batching**, which is orthogonal to whether you expose one tool or twelve. Meanwhile the high-level path has three unpriced costs: an LLM inference per call (latency + nondeterminism + a COGS line), the host losing visibility into failure modes, and Steel having to own model choice. Browserbase went all-in on it and has shipped zero releases in the four months since. And it violates PLAN.md's own non-goal.

Capture the batching win with `browser_batch(steps[])` and `include_snapshot` on action tools. Do **not** ship `run_task(natural_language)`. Revisit only if a host explicitly asks for delegation to save its own context — and then ship it as a Tasks-extension tool returning a handle, not a blocking call.

**Coordinate/vision surface for computer-use models: yes, as an opt-in second profile.**

Three facts settle this. (a) Computer use became a **native interleavable tool** inside frontier models in 2026 — Gemini 3.5 Flash declares it alongside function calling; GPT-5.4 (2026-03-05) is OpenAI's first general-purpose model with native computer use. A host can hold both surfaces in one conversation, so Steel doesn't have to pick. (b) A11y trees are **degrading**: WebAIM Million Feb 2026 found 95.9% of homepages with WCAG failures (up YoY), 46.3% with empty links, 30.6% with empty buttons, 51% missing form labels. A third to a half of interactive nodes will have no accessible name. A11y-only is not sufficient. (c) But pure-vision grounding tops out around **37.4%** on live tasks (MAG, arXiv 2607.10079, best frontier result GPT-5.5 with coordinates), and grounding preference is **model-specific** (Gemini prefers set-of-marks by +13.8 points; GPT-5.5 and Claude Sonnet 4.6 are indifferent) — so hard-coding v1's set-of-marks numbering is a bet against half the lineup.

Therefore: a11y-first default, `vision` profile opt-in, backed by Steel's `POST /v1/sessions/{id}/computer` (no CDP needed, screenshot in the same round trip). Do the pixel work server-side — default viewport 1280x720, pre-downscale preserving aspect ratio (Anthropic's benchmarked "single highest impact optimization" for click accuracy), document the coordinate space in the tool description, include a `zoom(region)` action (cheaper than re-screenshotting). Do **not** overlay coordinate grids or tile images — Anthropic measured no consistent uplift.

## 5. Page representation and token economics

### 5.1 The decision

**A11y snapshot is the default structured read. Markdown is the default stateless read. Screenshots are a resource link, opt-in inline, and the tool description tells the model not to act on pixels.**

Evidence, in order of weight:
- Playwright's own docs: a11y snapshot ≈ **200–400 tokens**; screenshot ≈ **3,000–5,000**.
- Anthropic's platform docs: a computer-use screenshot ≈ **1,000–1,800 input tokens**, plus 466–499 tokens of beta system-prompt overhead. (So the honest ratio is 4–9x, not the 50x some secondary sources quote — vision is affordable as an *escalation* per step, which is exactly the right posture.)
- Vercel's `agent-browser` compresses a page to 200–400 tokens with `@eN` refs on interactive elements only. One third-party benchmark: six tests at ~1,400 tokens vs ~7,800 with Playwright MCP.
- Every serious vendor gates coordinates behind a flag and writes anti-affordance text into the screenshot tool description. Playwright's says: *"You can't perform actions based on the screenshot, use browser_snapshot for actions."* **Copy that wording.** Telling the model not to act on pixels is measurably part of how these servers keep agents on the cheap path.

### 5.2 Element referencing — this closes PLAN.md open question #5

Both leaders converged independently on "refs must survive re-snapshotting, keyed on browser-level node identity, not snapshot position." Take the better half of each:

- **Key on `(loaderId, backendNodeId)` — Chrome's model, not Playwright's.** Chrome memoizes the uid in a per-page map keyed on `${loaderId}_${backendNodeId}`, so a surviving node keeps its uid across snapshots and only a real document load rotates it. This was a deliberate, changelogged decision (#814). Playwright instead invalidates when the ARIA role **or accessible name** changes — which means a button whose label flips `Save` → `Saving…` silently gets a new ref mid-flow. For a scrape-first server, Chrome's model is strictly better. Both are available over plain CDP; no Playwright dependency. **Implementation caveat (found against real Chrome in P1): never reset the ref counter per document.** A per-document counter means `@e1` taken before a navigation resolves to a completely different `@e1` afterwards — a silent correctness bug. With a page-lifetime counter, a pre-navigation ref always fails with a precise `page_navigated` staleness error instead, which is the whole point of versioned refs.
- **Assign refs only to nodes that are visible AND receive pointer events** — Playwright's `options.refs === 'interactable'` gate. Non-interactable nodes appear in the snapshot text with no ref, so the model *structurally cannot* target them. Free correctness win. **Implementation caveat (found against real Chrome in P1): this gate is not sufficient applied geometrically — it hands a ref to `<html>`.** And DOMSnapshot's `isClickable` is narrower than it sounds: it means "has a click listener", so a plain `<button>` is not marked clickable. Targetability needs `isClickable OR focusable OR an interactive ARIA role`, with an explicit deny list for document-level roles (`RootWebArea` etc., which Chrome marks focusable).
- **Keep off-screen and CSS-hidden nodes in the text.** Playwright's maintainers are right that whole-page comprehension is the core advantage over screenshots ("the agent can understand the entire page without needing to scroll"). Their real mitigation is the no-ref rule, not filtering. Consider an explicit in-viewport marker.
- **Version the refs.** Every snapshot carries a `snapshot_id`; every ref is `(snapshot_id, ref)`. On a stale ref return a *precise* tool-execution error: `ref @e12 belongs to snapshot s3; the page has changed and the current snapshot is s5 — call browser_find or browser_snapshot`. Every implementation surveyed handles staleness with "re-snapshot and hope." Versioning is cheap and is a real reliability differentiator.
- **Use the `@eN` vocabulary.** Steel's CLI vendors Vercel Labs' `agent-browser` (npm 0.33.0, updated 2026-07-23) for all non-lifecycle browser commands, Steel's five installed skills teach `click @e1`, and Steel's users already type it. A second incompatible ref format means Steel teaches two idioms and neither gets good. Either depend on the package or mirror its output exactly.
- **Synthesize names for unnamed nodes and mark them inferred.** Per WebAIM 2026, 30–46% of buttons and links have no accessible name. Fall back to nearest text / `aria-labelledby` / `title` / `alt` / `placeholder` / `name`, and flag it so the model discounts the guess.

### 5.3 Context management

- **Post-action snapshots default OFF.** PLAN.md says `browser_navigate` "Returns page snapshot." That is Playwright's choice and it is the direct cause of ~10 separate context-bloat issues over eight months (#1185, #1203, #1216, #1233, #1274, #1290, #1329, #1573, monorepo #41395, #41444; #1290 measures Playwright's default tool list alone at 14.4k tokens = 7.2% of Claude's window). Chrome shipped the opposite as a deliberate change ("allow skipping snapshot generation for input tools", #821). Steel is positioning as the token-cheap option and then adopting the token-expensive default. Return a one-line outcome plus a cheap change signal; `include_snapshot: true` is the opt-in.
- **Budget: 25,000 tokens** is Claude Code's default tool-response cap. Set every text-returning tool well under it with a cursor.
- **Reference over value, but Steel's version is harder than everyone else's.** Playwright (`filename`, `--output-mode file`, `--output-dir`, `--output-max-size` with eviction), Chrome (`filePath`), and Mozilla (`saveTo`) all write to the **client's** disk. `mcp.steel.dev` cannot. Steel's answer must be **MCP resource links + short-lived signed URLs on Steel's CDN**, with `resources/read` supporting byte/line ranges so the model can page through a huge payload. This is an architecture decision for P2/P3, not P5 polish. Mozilla's `saveTo` + `preview: <N chars>` pair is the best design of the three and the least known — it makes reference-over-value ergonomic instead of blind. Copy it.
- **Nobody is measuring response bytes, only schema bytes.** Every published number in this space (including all of §3's) is `tools/list` size. But the actual complaints are about *responses* — one large a11y snapshot dwarfs the entire tool catalog. Steel's real budget is **bytes-per-turn**. Add CI assertions on both: fail the build if `tools/list` exceeds a per-profile byte budget, and if a reference-page snapshot regresses.
- **Adopt a fixed sectioned response envelope** (Playwright's shape: `### Error` / `Result` / `Code` / `Page state` / `Snapshot` / `Console` / `Downloads`). Skimmable, per-section truncatable, testable.
- **Consider a `### Code` section** emitting equivalent steel-sdk or Playwright source for every action, toggled by a flag. That turns an exploratory agent session into a reusable Steel script — squarely on-strategy for Steel's skills and automation products, and no competitor offers it against a cloud browser.
- **Auto-settle after every action, and never expose `networkidle`.** Implement chrome-devtools-mcp's `WaitForHelper`: (1) listen for `Page.frameStartedNavigating` for a ~100ms window, ignoring `historySameDocument`/`historyDifferentDocument`/`sameDocument`; (2) if a real navigation started, await it with a ~3s budget; (3) await DOM quiescence via an in-page MutationObserver on `document.body {childList, subtree, attributes}` resolving after a 100ms quiet period, capped at ~3s. **Scale every budget by a network multiplier** — Steel sessions run through proxies and are systematically slower than localhost; the stock constants will be too tight. Without implicit auto-settle, agents call `browser_wait_for` defensively after every action, burning a round-trip each time — worse than the auto-snapshot you're avoiding.
- **Never return a bare "success" from an interaction.** chrome-devtools-mcp #2199 (open, unreproducible by maintainers, 8 comments) is silent input loss where the tool reports `Successfully clicked on the element` while zero DOM events fired. That is the worst possible agent failure mode — the model concludes the app is broken. The settle helper computes `navigatedToUrl` and mutation state for free. If a click produced no navigation, no mutation and no focus change, **say so** so the model can escalate.
- **Set `ttlMs` + `cacheScope` deliberately.** `tools/list` is org-independent and stable → long `ttlMs`, `cacheScope: 'public'`, deterministic tool ordering (real prompt-cache payoff, one-line discipline). **Every result derived from an authenticated principal → `cacheScope: 'private'`.** Getting this wrong is exactly the Asana failure mode (see §7).
- **Consider a columnar text encoding for repeated records** (network lists, link lists, table extractions) while keeping `structuredContent` canonical JSON. chrome-devtools-mcp has TOON landed behind a flag and GCF via `experimentalGcfFormat` in v1.6.0, with `structuredContent` byte-identical. Cheap, contained, right compatibility pattern.

### 6.1 Decisions

| Decision | Choice | Rationale |
|---|---|---|
| Protocol | **2026-07-28 primary**; 2025-11-25 / 2025-06-18 via the SDK legacy shim | `createMcpHandler(factory)` defaults to `legacy: 'stateless'` and `serveStdio(factory)` to `legacy: 'serve'`. | SDK | `@modelcontextprotocol/server@^2` + `@modelcontextprotocol/node`; `@modelcontextprotocol/client` in tests | v1 is frozen at 1.29.0 (2026-03-30). Scaffold on `2.0.0-beta.5`, bump to stable. Budget for **Node ≥20, Zod ≥4.2, `"type": "module"`** at P0 — painful to retrofit. Codemod exists: `npx @modelcontextprotocol/codemod@beta v1-to-v2 .`. Pin exact versions: `latest` currently points at a beta |
| Transport | Streamable HTTP. `GET`/`DELETE` → `405`. Origin + Host validated in middleware (`createMcpHandler` "validates nothing" — use `localhostHostValidation()` / `hostHeaderValidationResponse`) | Spec |
| Response mode | **Do not pin `responseMode: 'json'`** on tools that report progress — JSON mode drops mid-call notifications. Send `X-Accel-Buffering: no` and periodic SSE comment keep-alives (`:\r\n`) | These silently break 60s browser actions behind nginx/Cloudflare. The SDK only landed keep-alive frames for the web-standard transport on 2026-07-27 (#2541) |
| State | **Explicit `session_id` handles.** No protocol session, no `Mcp-Session-Id`, no sticky routing | SEP-2567. The spec's worked example is a browser context |
| Store | Redis (or Postgres) as a **handle registry** only: `session_id → {finished_session_id, org_id, project_id, created_at, last_used_at, region}`. **No SSE event store.** Reuse the same store for future Tasks state — build the TTL/reaper machinery once | |
| Server shape | Plain **stateless Node container** behind round-robin, co-located with the Steel browser fleet. Same image for self-host with an in-memory registry when Redis is absent | Cloudflare's `McpAgent` (Durable Object per session) optimizes for the abstraction the spec just deleted, and couples you to Workers. Vercel's model fights long-lived streams |
| DI shape | **Module-scope pools/clients/registry, closed over by a per-request server factory.** `createMcpHandler` runs the factory *once per HTTP request*: "create connection pools and caches once at module scope and close over them" | This is a different shape from PLAN.md §4's `buildServer(deps) → long-lived McpServer`. Rethink before P0, not after |
| Auth | `Authorization: Bearer <STEEL_API_KEY>` **and** a query-param key, at launch | Browserbase (`?browserbaseApiKey=`), Bright Data (`?token=`), Browserless (`?token=`, checked after the header, before OAuth JWT) all ship the query param because many hosts still can't set headers and `mcp-remote` friction loses users. | Observability | Structured JSON to stderr (now spec-endorsed) **+ OpenTelemetry**, extracting W3C trace context from `_meta` `traceparent`/`tracestate`/`baggage` (SEP-414). And set the required `MCP-Protocol-Version`/`Mcp-Method`/`Mcp-Name` header-vs-body validation path to return `400` + `-32020`, verified in the integration suite.

### 6.2 "How do we guarantee we never leak a billed browser session"

The honest answer is **five layers, and the strongest one is not ours**. PLAN.md's chain has its most reliable leg deleted by the spec and is missing a new leak vector entirely.

| # | Layer | Mechanism | Survives |
|---|---|---|---|
| 1 | **Steel-native `inactivityTimeout`** | Set `timeout: min(plan_max, requested)` and `inactivityTimeout: ~120000` on **every** `POST /v1/sessions` | our process dying, replica rescheduling, network partition, client vanishing. **This is the guarantee. Everything else is an optimization** |
| 2 | **Steel-native `timeout` hard cap** | Derived from `GET /v1/details` (15 min Launch / 1 hr Scale), never hardcoded | same |
| 3 | **Client-minted `sessionId` UUID** | Generate the UUID ourselves and pass it as `sessionId` on create | the create-then-crash gap PLAN.md §12 #6 worries about — we know the id *before* create returns, so a crash mid-create leaves a sweepable, known id. `namespace` is a coarser second handle. (There is no `metadata` field; §12 #6's proposed mechanism doesn't exist) |
| 4 | **Explicit `browser_session_release`** | A real tool the model can call, with the retention policy stated in `browser_session_create`'s description so the model can see the cost | nothing on its own; it's the fast path |
| 5 | **Abort on stream close** | Plumb `ctx.mcpReq.signal` into **every** CDP call and abort the page operation | **This is the new leak vector PLAN.md misses.** On Streamable HTTP, closing the SSE response stream IS the cancellation signal; there is no `notifications/cancelled`. A client hang-up mid-navigate otherwise leaves a browser burning minutes with nobody listening |
| 6 | **Our reaper** | Sweeps the handle registry, releases idle/expired/orphaned handles | replica-local failures; reclaims concurrency slots faster than Steel's timeout would |

Instrument a counter per release path (explicit / stream-close / reaper / Steel `inactivityTimeout` / Steel hard `timeout`) and **alert on the Steel-backstop count** — that's the leak metric. Publish it as an SLO; a local MCP server structurally cannot offer this (Playwright #41918: 82 orphan Chromium processes, closed as "the client's problem"). Steel owns both ends and the leak costs the customer money, so "client's problem" is not an available answer.

**One thing to escalate to the platform team this week:** Kernel bills per-second and implements **Standby Mode** — when network activity stops the unikernel snapshots and *incurs zero cost while idle*, restoring exactly as it was. That is structurally better than any reaper: the leaked session costs nothing rather than being killed. If Steel can bill active-seconds-only or snapshot-and-suspend, this entire risk class collapses and it is a headline feature. If Steel cannot, Kernel will market zero-cost-idle against us and our reaper timings become a customer-visible tradeoff we have to defend.

**Also non-negotiable, and higher severity than the billing leak:** authorization-check the handle on **every single call**, from the request's own credential, never from anything cached at creation time. Namespace handles as `<org_id>:<handle>`, generate with ≥128 bits of CSPRNG entropy, opaque prefix (`sess_`), never derived from org id or timestamp. Per the spec's session-hijacking guidance, a session handle must never be a bearer capability on its own. A leaked handle grants a stranger a live, possibly logged-in browser. This is *exactly* the Asana root cause: cached results served across orgs without re-verifying tenant context, ~2 weeks, 1000+ customers.

## 7. Security

### 7.1 The threat list that actually applies

Ranked by (probability × blast radius) for a hosted, multi-tenant browser MCP server.

| # | Threat | Status | Mitigation we will implement |
|---|---|---|---|
| 1 | **Indirect prompt injection via page content** | **No protocol answer exists.** The spec's Security Best Practices page covers confused deputy, token passthrough, SSRF, session hijacking, local compromise, OAuth URL validation, scope minimization — and says **nothing** about prompt injection or sanitizing untrusted third-party content. The only normative hooks are the Tools page's one-liners: servers MUST "sanitize tool outputs," clients SHOULD "validate tool results." Five competing SEPs (1561 `unsafeOutputHint`, 1560 `secretHint`, 1487 `trustedHint`, 1913, 1984) are still in review. Field data is getting worse: Google measured **+32% relative** malicious injected content Nov-2025→Feb-2026 across 2–3B pages/month; Unit 42 (2026-03-03) mapped **22 delivery techniques** in active use — 37.8% human-invisible plaintext, 19.8% HTML attribute cloaking, 16.9% CSS suppression, 85.2% with a social-engineering frame. CSA logged real incidents (GrafanaGhost markdown-render exfil, forced $5,000 PayPal transfers). *Counterweight: model-layer resistance improved dramatically — Claude Sonnet 4.6 reports 1.29% Best-of-N browser injection success vs 49.36% for Sonnet 4.5, and Anthropic runs classifiers on `computer_20251124` screenshots at zero latency cost.* | **(a)** Strip before the snapshot leaves the server: zero-width characters, `display:none`/`visibility:hidden`/off-screen nodes, HTML comments, `aria-label` on non-rendered nodes. **(b)** Fence all page-derived text in an explicit untrusted-content delimiter with a provenance header — final URL after redirects, fetch timestamp — and an explicit statement that the enclosed text is data, not instructions. **(c)** Same standing instruction in the server `instructions` field. **(d)** `openWorldHint: true` on every tool. **(e)** Never echo page content into tool *descriptions* (chrome-devtools-mcp #2242 was exactly this, via third-party tool discovery). **(f)** Never render page content into a markdown image or link that could exfiltrate on render. **(g)** Optional `allowed_origins` that refuses cross-origin navigation. **(h)** Document the residual risk plainly: this reduces, it does not eliminate. Masking (arXiv 2607.05277) is a credible later feature and costs 5–25% task success |
| 2 | **Cross-tenant handle abuse** | A `session_id` that isn't re-authorized per call is a bearer token for someone else's live, logged-in browser. Integration test: cross-org handle rejection |
| 3 | **Cross-tenant cache leak** | The Asana incident: cached results served across orgs without re-verifying tenant context, ~2 weeks, 1000+ customers. | 4 | **Credential/secret leakage into model context** | Playwright #1566: password input values serialized as plaintext into the a11y tree; closed with "use the `--secrets` feature," itself documented as "a convenience and not a security feature" | **Redact `input[type=password]` values from snapshots.** Support a secrets/redaction map. Never expose credential-creation as a tool |
| 5 | **API key in a URL** | Browserbase ships `?browserbaseApiKey=<raw account key>`. | 6 | **Arbitrary eval** | Correctly excluded from the hosted default | `full`/self-host profile only, off by default, explicit server flag, name it so the danger is unmissable |
| 7 | **DNS rebinding / Origin** | `createMcpHandler` explicitly validates nothing — no Host, no Origin, no token | Mount validation in front. PLAN.md §5's Origin-403 requirement is correct and is on us, not the SDK |
| 8 | **Token passthrough / confused deputy** | Spec: "MCP servers MUST NOT accept any tokens that were not explicitly issued for the MCP server" | Note this means a Steel API key presented as an OAuth bearer is not OAuth-conformant — it's a separate, non-OAuth scheme and should be documented as such |

### 7.2 Human-in-the-loop is a feature, not just a mitigation

Adopt **MRTR** rather than inventing something. When a session hits a login wall or CAPTCHA:

```
inputRequired({
  inputRequests: { solve: inputRequired.elicitUrl({
      message: 'Solve the CAPTCHA in the live browser, then retry',
      url: <Steel debugUrl — /v1/sessions/{id}/player; interactivity is the session's debugConfig, not a URL param> }) },
  requestState: await codec.mint({ org, handle, exp })
})
```

The client retries the original request with a different JSON-RPC id. The SDK's legacy shim converts this into a real `elicitation/create` push for 2025-era clients, so handlers are written once with no branching. Cloudflare and Human Browser both market HITL as a headline feature; Steel already has the live interactive viewer. **This belongs in P2/P3, not P5** — it is arguably the highest-value thing a browser MCP server can do that a scraper API cannot, and it is a large part of the answer to PLAN.md §12 #4 (anti-bot parity).

### 7.3 Failure classification is the sleeper differentiator

Steel has already invested heavily here and PLAN.md doesn't use any of it: five installed skills encoding a bot-detection / proxy / auth / agent-behaviour taxonomy with a prescribed mitigation ladder, standardized `{message, error, linkToDocs}` API errors with genuinely good prose, and an agent-traces API. Google's design principles call this "Self-Healing Errors: return actionable errors that include context and potential fixes." PLAN.md picks the SEP-1303 *mechanism* and never specifies error *content* — which is where the value lives.

Concrete mappings to implement:

- `402` → "Steel-managed proxies and CAPTCHA solving need a $10 verified paid balance on Launch (free credits don't count). Retry without `use_proxy`, or supply your own via `proxy_url`." **This is the most likely surprise failure for a new Launch user pointing an agent at a protected site, and it is invisible unless we translate it.**
- `429` → say *which* limit: the 10-session concurrency cap, the 60 RPM general limit, or the separate 20 RPM Browser Tools cap. Include `Retry-After`.
- `403` + Cloudflare / DataDome / PerimeterX / Akamai / `cf-chl` / `chal_t=` / `/sorry/` / `__cf_bm` markers → "this is bot detection, not a bug. Next rung: `use_proxy: true`, then `profile_id`." Follow the skills' ladder — identity first, then pacing and lower concurrency, then proxies, then CAPTCHA, then stealth tuning. **Never all at once.**
- `ERR_TUNNEL_CONNECTION_FAILED` / `407` → proxy config.
- Stale `@eN` → name the ref, the reason (role/name changed, node removed, page navigated), and the recovery action.
- Blocked click → **name the covering element** (`covered by <div#consent-banner>`), as `agent-browser` does. Turns the single most common browsing failure into a self-correctable one.
- Self-host capability gaps → named errors, not opaque 400s. **Self-hosted Steel is concurrency 1**: a second `browser_session_create` must fail with "self-hosted Steel supports one browser session at a time; release the current one first." `profile_id`, `credentials`, `use_proxy: true`, `region`, files and CAPTCHA solving must all fail with named capability errors.
- Pass Steel's `linkToDocs` through verbatim. Suppress only the 401 body's false claim that Bearer isn't supported.
